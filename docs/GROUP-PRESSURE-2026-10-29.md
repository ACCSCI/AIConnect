# 群容量压力测试 · 2026-10-29

本报告保留修复前基线。2026-10-30 已修复入站拒绝及群投递并发问题，复测见 [群投递背压修复](GROUP-BACKPRESSURE-2026-10-30.md)。

**结论：默认保留 16 人。32/64 人可显式创建实验群，但暂不作为默认。**

## 测试范围

同一台 Windows x64、16 逻辑处理器、约 31.2 GiB RAM。每个模拟节点是独立 Release Rust 守护进程，独立身份、SQLite、UDP 端点和本地认证 IPC；每节点 2 个 Tokio 工作线程。测试仅走原生 iroh 直连，不调用模型，不部署。它不代表真实异网、公网中转或 64 台物理机器容量。

每档 16 条串行发起广播、8 条广播以 4 个发送者并发；正文 256 字节。串行指前一次 API 返回后再发，pending 仍可能在后台补投。第一轮保留冷连接/积压影响；复测先排空预热并加全员 ACK 只读观测，第三轮采用复测方法确认最终构建。第一轮与后两轮不是严格相同初态，不做合并统计；后两轮机器后台内存占用也有变化，记录在原始数据内。

送达按所有接收节点 SQLite 历史独立核对，排除发件人自己的本地副本。发送入口拒绝、已经入队、全员 ACK 三种状态分开记录。复测全员 ACK 延迟包含重试，约 100 ms 观测分辨率；它不等于第一次 API 返回时间。

## 最终构建确认轮结果

| 节点 | 串行全员 ACK P50 / P95 | 并发全员 ACK P95 | 并发请求受理 | 已受理消息最终送达 | 通信进程私有内存采样峰值合计 |
| --- | --- | --- | --- | --- | --- |
| 16 | 0.08 s / 0.11 s | 18.26 s (8 条受理样本) | 8/8 | 100% | 177.5 MiB |
| 32 | 0.49 s / 1.22 s | 17.17 s (7 条受理样本) | 7/8 | 100% | 310.9 MiB |
| 64 | 5.00 s / 20.38 s | 20.73 s (8 条受理样本) | 8/8 | 100% | 495.9 MiB |

P95 样本量为串行 16 条、并发最多 8 条，适合定位问题，不是生产 SLA。内存只计通信进程，不包括模型；工作集合计也已记录，但可能重复计算共享页，表中采用 PrivateBytes 采样峰值。

## 首轮对照与拒绝原因

| 节点 | 串行受理/请求 | 并发受理/请求 | 全部请求口径最终送达率（串行 / 并发） |
| --- | --- | --- | --- |
| 16 | 16/16 | 8/8 | 100.00% / 100.00% |
| 32 | 16/16 | 6/8 | 100.00% / 75.00% |
| 64 | 15/16 | 6/8 | 93.75% / 75.00% |

三轮所有已经入队的消息均获得全部收件人 ACK，并经接收端历史核对；低于 100% 的全部请求送达率来自发送入口失败，而不是已受理消息静默丢失。失败请求返回 `aborted by peer: the server refused to accept a new connection`，发送方数据库没有对应 outbox 项。

代码中的入站并发上限为 32，满载直接 `incoming.refuse()`。群主既处理发件人校验，又处理各收件人的新鲜成员校验；群发扇出会放大控制连接数。16/32/64 成员快照分别约 6.7/13.2/26.2 KB。该瓶颈仍未优化，本轮没有调高连接并发来美化结果。

16 人虽然三轮没有入口失败，但复测并发全员 ACK P95 达 18.22 秒。32 人在预热排空后的复测表现更快，但首轮仍有 2/8 并发请求未受理，不能凭一次较好结果提高默认容量。64 人复测串行尾延迟约 29.91 秒，并发仍有入口拒绝。默认 16 是相对保守容量选择，不代表并发实时性已解决。最终构建确认轮中，16/32/64 人并发全员 ACK P95 分别为 18.26/17.17/20.73 秒；32 人有 1/8 请求未受理，64 人本轮全部受理，但不能抹去前两轮已出现的拒绝。

## 群主离线与恢复

三档、三轮共 27 次群主离线发送尝试全部在约 8 秒后返回 `peer_unreachable`，没有将未经授权的尝试落入群消息记录。群主用原身份和数据库重启后，成员数保持，恢复广播全部送达。

## 已落实的配置

默认仍为 16；群容量作为签名策略写入群状态。显式 `group create --max-members 32` 或 `64` 可用于实验；所有节点需要当前构建。旧群保持原上限，缺少该字段的早期群按 16 处理。联系人/邀请通用签名大小边界未放宽；群快照单独限制在 44 KB 以内，仍小于 RPC 帧上限。

下一步应先修入站背压、群发并发调度及初始授权失败重试，再在相同负载下复测，而不是继续放宽默认人数。
